# FootOps 产品需求说明

> 文档类型：产品需求基线
> 基线日期：2026-07-31
> 产品阶段：FootOps Analyst MVP
> 目标用户：足球战术爱好者、足球内容创作者、战术分析学习者
> 黄金任务：分析一名球员在连续多场比赛中的战术角色变化

## 1. 文档目的

本文档只回答三个问题：

1. FootOps 为谁解决什么问题；
2. 第一版必须提供哪些功能；
3. 什么结果才算满足需求。

Agent 数量、Harness、AgentScope、MCP 和数据库选型不属于本需求文档，统一
记录在 [FOOTOPS_MINDBRIDGE_ARCHITECTURE.md](./FOOTOPS_MINDBRIDGE_ARCHITECTURE.md)。

## 2. 产品定位

FootOps Analyst 是一个面向足球战术爱好者和足球内容创作者的**可验证战术
分析与学习工具**。

当前 MVP 的真实交付边界是：以公开事件数据为基础，分析**单个球员在连续多场比赛中的
描述性指标变化**。它还不是完整的单场比赛复盘、球队战术分析或自动战术解说系统；后两者
需要更多事件指标、比赛级数据模型和案例知识库，列入后续阶段。

它结合公开、合法可用的职业比赛数据与可追溯的足球规则、战术知识，将用户的自然语言
问题转化为：

- 可检查的数据和指标；
- 同时区分数据事实、战术知识和待验证的战术假设；
- 跨比赛趋势图或区域图；
- 可编辑的战术板；
- 可继续追问和局部修订的分析工作区；
- 可导出的内容初稿。

FootOps 不对标职业俱乐部的内部分析系统。MVP 不使用俱乐部私有视频、追踪
数据、训练负荷和医疗数据，也不提供职业训练、医疗或比赛决策建议。

## 3. 目标用户

### 3.1 第一优先级

1. 希望系统学习足球战术分析的数据型球迷；
2. 制作文章、视频或播客的足球自媒体创作者；
3. 需要练习比赛复盘方法的战术分析学习者。

### 3.2 非主要用户

- 只查询比分和赛程的普通用户；
- 博彩和投注用户；
- 职业俱乐部教练组；
- 职业球探和医疗部门；
- 需要实时比赛指挥的用户。

## 4. 用户问题

一次有数据依据的战术分析通常需要用户手工完成：

1. 寻找比赛、阵容和事件数据；
2. 清理不同数据源的字段；
3. 计算触球区域、推进、传球、关键传球和基础射门参与指标；
4. 跨比赛对齐样本和统计口径；
5. 将数据变化组织为可审核的描述性观察；将其解释为战术角色变化仍需要知识检索和额外审核；
6. 查找适用的足球规则、战术概念、案例和分析模板；
7. 检查结论是否同时超出比赛数据和战术知识能够支持的范围；
8. 另外使用绘图工具制作战术板；
9. 把结论、图表和引用整理成内容初稿。

FootOps 的价值不是增加一个足球聊天窗口，而是把这条分散流程组织成一个
可执行、可检查、可恢复和可重复使用的研究工作区。

## 5. 第一版黄金任务

MVP 首先完整做好一个任务：

> 分析一名球员在连续 3 至 10 场比赛中的战术角色变化。

典型问题：

> 某名中场最近 5 场的位置是否更靠前？这种变化是稳定的角色调整，还是由
> 个别比赛状态造成？请给出数据依据，并画出主要接球区和推进路线。

### 5.1 标准输入

- 赛事；
- 球队；
- 球员；
- 3 至 10 场比赛或明确日期范围；
- 用户希望验证的战术问题；
- 可选的比赛阶段、对手、阵型或指标偏好。

### 5.2 标准输出

1. 一句描述性摘要，不把统计变化直接写成因果结论；
2. 3 至 10 条结构化 Finding；
3. 每条 Finding 对应的指标、来源、时间范围和限制；
4. 若请求进入知识链，给出采用的规则或战术概念及其来源；案例和模板检索属于后续增强能力；
5. 将事实、知识引用和待验证推断分开；
6. 跨比赛趋势图或区域图；
7. 一张可编辑的战术板；
8. 可继续缩小范围、增加场次或调整口径的上下文；
9. 可导出的分析摘要。

## 6. 功能需求

### 6.1 P0：MVP 必须完成

| 编号 | 功能 | 用户行为 | 系统交付 |
| --- | --- | --- | --- |
| FR-01 | 创建分析工作区 | 输入球员、球队、比赛和问题 | 标准化实体、时间范围和数据覆盖 |
| FR-02 | 球员角色变化分析 | 分析连续多场比赛 | 描述性趋势指标和关键事件，不直接承诺战术因果 |
| FR-03 | 数据与指标检查 | 展开任一结论 | 指标值、计算口径、样本和来源 |
| FR-04 | 证据审核 | 查看证据状态 | 支持、需补证、降级或拒绝 |
| FR-05 | 图表生成 | 查看变化趋势 | 由真实指标驱动的确定性图表 |
| FR-06 | 战术板生成与编辑 | 将 Finding 同步到战术板 | 位置、区域和样本内移动箭头；跑位和传球线路待后续数据支持 |
| FR-07 | 连续追问 | 修改比赛范围或观察条件 | 保留工作区并更新受影响产物 |
| FR-08 | 分析恢复 | 重新打开历史分析 | 恢复问题、数据、结论和战术板 |
| FR-09 | 报告导出 | 选择已审核结论 | 带引用、图表和战术板的摘要 |
| FR-10 | 规则与战术知识检索 | 询问规则、概念或案例 | 带版本、章节和来源的知识回答 |
| FR-11 | 联合战术推理 | 提出需要解释比赛数据的战术问题 | 目标能力；当前仅完成首个数据 + 战术概念 Artifact 切片 |
| FR-12 | 有限修订 | 审核发现证据不足或冲突 | 补检索、修订、降级或拒绝，不无限循环 |

### 6.2 P1：P0 稳定后扩展

- 单场比赛的推进、压迫和防守结构分析；
- 两场比赛或两个时间段的战术对比；
- 球队层面的比赛阶段分析；
- 内容创作者使用的文章、视频和播客提纲模板；
- 用户保存的分析偏好。

P1 必须复用 MVP 的 Workspace、指标、证据和战术板数据结构，不得另建一套
互不兼容的流程。

## 7. AnalysisWorkspace 需求

每次分析必须形成可持久化的 `AnalysisWorkspace`，至少包含：

- 用户问题、分析范围和验收条件；
- 使用的数据快照和指标口径；
- 当前运行状态；
- 数据、指标和 Finding；
- 证据审核结果和引用；
- 图表和战术板；
- 用户修订记录；
- 最终报告。

聊天消息不是唯一业务状态。页面关闭后，Workspace 应能够重新打开。

## 8. 数据与真实性要求

- 正式结果不得使用前端写死的分析数据；
- 比赛事实必须来自带来源和获取时间的数据快照；
- 指标必须由确定性代码计算，不能由语言模型心算；
- 数据覆盖不足时必须明确说明，不得补造缺失比赛；
- 演示数据必须显示“演示”状态，不得伪装成真实分析；
- 每个数据源必须记录覆盖范围和使用限制；
- 第一版黄金样例必须先通过数据覆盖审计，再确定具体球员；
- 模型生成的解释不得覆盖或修改原始指标值。
- 应从数据 Provider 获取的比赛事实不得作为 RAG 文档事实源；
- 规则和战术知识必须记录发布机构、文档版本、章节、来源 URL 和适用范围；
- 足球竞赛通则优先使用 IFAB Laws of the Game，FIFA 资料按赛事规程或官方解释单独入库；
- 未授权战术资料和未审核的模型输出不得进入正式知识库。

## 9. 用户界面需求

必须提供：

- 可折叠侧边栏；
- 问答和分析工作区；
- 数据范围与比赛样本展示；
- 证据引用与证据面板；
- 跨比赛趋势图；
- 可编辑战术板；
- 报告预览和导出；
- 桌面与移动端响应式布局；
- 加载、数据不足、失败、取消和恢复状态；
- 演示模式与真实数据模式的明显区分。

普通用户只看到业务状态：

| 系统内部状态 | 用户可见表达 |
| --- | --- |
| 正在调用数据工具 | 正在检索比赛数据 |
| 正在检索规则或战术知识 | 正在查找相关规则与战术案例 |
| 正在执行证据审核 | 正在交叉验证 |
| 正在进入补证循环 | 正在补充证据 |
| 工具失败重试 | 数据源响应较慢，正在重试 |
| 运行轨迹 | 不在普通用户界面展示 |

不得向普通用户展示原始 Chain of Thought、Token 预算、内部 Agent 名称或
Runtime 调试信息。

## 10. 非功能需求

### 10.1 可追溯

- 每个关键数值关联数据快照和计算口径；
- 每条重要结论关联指标或知识来源；
- 每个 AI 生成的战术板标记关联 Finding；
- 报告记录数据、Skill 和模型版本。

### 10.2 可恢复

- 页面刷新不丢失已保存 Workspace；
- 数据源超时后可以重试；
- 长任务可以取消；
- 复杂分析可以从最近可用状态恢复；
- 用户修改范围后只更新受影响结果。

### 10.3 可测试

- 数据适配器拥有固定 Fixture；
- 指标计算拥有确定性单元测试；
- 正式发布前运行黄金任务回归；
- 演示数据和真实数据使用相同业务 Schema。

### 10.4 性能

- 流式状态必须先于完整结果返回；
- 简单确定性查询不得启动复杂 Agent 链路；
- 图表和战术板由前端确定性渲染；
- 长报告和高清导出允许异步执行。

## 11. 为什么需要 Agent

以下工作需要 Agent：

- 识别自然语言中的实体、范围和歧义；
- 判断请求需要普通对话、规则知识、战术知识、比赛数据，还是数据与知识联合分析；
- 根据问题制定有边界的分析计划；
- 选择分析方法、数据工具和指标工具；
- 数据缺失或证据冲突时调整计划；
- 将多个指标组织为战术解释；
- 判断结论是否需要补证、降级或拒绝；
- 根据追问只修订受影响的结果。

以下工作不使用 Agent：

- 比分、赛程、积分榜和已有统计查询；
- 指标公式计算；
- Schema、数值一致性和权限校验；
- 图表、战术板和报告的确定性渲染；
- 数据库事务、缓存和限流。

FootOps 的独立价值来自固定数据边界、结构化产物、可恢复工作区、证据标准
和面向内容生产的重复流程，不是声称模型比 Codex 等通用 Agent 更聪明。

## 12. MVP 非目标

- 不提供博彩、投注建议或比分保证；
- 不把模型猜测包装成实时伤停、阵容或转会事实；
- 不承诺拥有当前西甲完整事件级或追踪数据；
- 不对所有请求强制启用多 Agent；
- 不把“接入 RAG”本身当作卖点；RAG 必须服务于规则、战术案例、指标口径和分析模板；
- 不为了展示自主性而允许无限循环；
- 不在 MVP 中实现视频自动事件识别；
- 不直接生成职业俱乐部级训练或医疗决策；
- 不在用户端展示模型的 Chain of Thought。

## 13. MVP 验收标准

当用户提交一个受支持的球员角色变化问题时，系统必须能够：

1. 说明选择了哪些真实比赛和数据源；
2. 用代码计算至少一组跨比赛指标；
3. 返回与指标绑定的 Finding；
4. 对证据不足的结论执行降级；
5. 对复杂战术解释同时给出比赛数据引用和战术知识引用；
6. 区分事实、知识和推断，并允许审核结果触发一次或有限次数修订；
7. 动态渲染趋势图和战术板；
8. 接受“只看上半场”或“增加一场比赛”等追问；
9. 保存并恢复 Workspace；
10. 导出带引用的分析摘要。

量化指标和对照实验记录在架构文档的 Engineering Harness 章节。

## 14. 需求变更规则

- 新功能必须标记为 P0、P1 或后续版本；
- P0 变更必须说明对黄金任务的影响；
- 不能因为框架提供某项能力就把它自动加入产品需求；
- 数据源无法支持的功能不得进入 P0；
- 需求、架构和开发顺序发生冲突时，以本需求文档的用户价值和验收标准为先。
